# Contributing

Work locally, inspect Git first, and preserve existing uncommitted work. The
owner has authorized a five-book selected collection and the literal language
forms recorded in configuration. Do not expand it, overwrite editorial decisions
or publish/push without a new explicit instruction. Read AGENTS and the policies.

For every text, note, claim, code or asset contribution, disclose:

- Your actual identity/role and the source material used, with exact edition,
  locator and eligibility or original authorship. Free online access is not a
  license. Do not submit protected translation wording as a rewrite input.
- Any AI assistance, the tool/model identifier actually visible (unknown/null
  when not exposed), date, prompt/input packet and returned artifact where lawful.
  Do not invent model versions, evidence, expertise, approvals or endorsements.
- That you hold or have appropriate permission for the rights contributed and
  agree to MIT for original software and associated software documentation, or
  CC0-1.0 for your eligible original editorial contributions, as applicable.
  Preserve upstream licenses/obligations; you cannot waive another person's rights.

These statements are required contributor rules, not a representation that every
AI output is protectable or cleared. A model cannot attest as a human editor.
Record peer/expert reviews only if actual people performed them. Owner approval
must not be described as scholarly validation merely because the owner accepted it.

Keep raw source bytes, faithful transcription, modernization proposals, approved
text and original commentary distinct. Changes to main text require exact owner
review; notes require separate content-hashed approval and dependent text hashes.
Never delete uncomfortable passages, fill missing text from memory, fabricate
native names, harmonize inconsistent accounts, or bulk-copy modern study notes.

Run the offline README checks for relevant code changes. Keep fixtures synthetic
or exactly eligible, labelled and licensed. Tests prove software behavior only.
When a schema changes, version it or document compatibility and update its
meaningful rejection tests. Record actual commands, limitations and the next
small task in PROGRESS and NEXT_STEPS. Use GitHub Desktop to inspect local changes;
there is no automatic commit, push, site deployment or public release.
